## Runtime and private pairing

- The Linux server tarball includes its own Node runtime, launcher `bin/orca-ide`, native PTY helper and RPC-delivered mobile client bundle. It needs no Electron or active desktop. The package omits the desktop browser UI. Its `/web-index.html` and renderer allow-list manifest are both present in the same-version Debian package at `./opt/Orca/resources/app.asar.unpacked/out/renderer/`. Extract that directory to `out/renderer` under the server tarball's root. The bundled launcher finds it there. The HTTP handler maps both `/` and `/web-index.html` to the real frontend. Preserve WebSocket upgrades on `/`. [Browser bundle lookup](https://github.com/stablyai/orca/blob/v1.4.268/src/shared/web-client/bundled-web-client-root.ts), [static route code](https://github.com/stablyai/orca/blob/v1.4.268/src/main/runtime/rpc/transports/websocket/static-web-client-handler.ts)
- Run `orca-ide serve --port 6768 --bind 0.0.0.0 --pairing-address wss://orca.home.arpa --refuse-public --supervise --no-pairing` inside an isolated container, restricting access at the container network, host and reverse-proxy boundaries. A native loopback-only bind blocks on-demand network pairing. Orca attempts to widen the listener when creating a network offer and correctly refuses to override an explicitly pinned loopback address. Network admission within Orca sees the reverse proxy's source, so the proxy and host policy must restrict the actual client. [Serve flags](https://github.com/stablyai/orca/blob/v1.4.268/src/cli/specs/serve.ts), [pairing bind behavior](https://github.com/stablyai/orca/blob/v1.4.268/src/main/runtime/rpc/server/pairing/pairing-offer-requests.ts)
- Mint the desktop and browser offer privately on the running runtime with `orca-ide pair --address wss://orca.home.arpa`. Add `--mobile` for a native phone link. Browser credential material is a URL fragment and stays out of proxy requests. Treat both forms as secrets and use separate links for separate clients. Serve startup logs suppress offers under `--no-pairing`. The browser cannot revoke runtime grants from its web UI in this version. The documented local recovery is to stop the service and run `orca-ide serve reset-identity` as its service account, which revokes all grants and requires re-pairing. Active users should coordinate before this disruptive operation. [Pair CLI](https://github.com/stablyai/orca/blob/v1.4.268/src/cli/specs/pair.ts), [web API limits](https://github.com/stablyai/orca/blob/v1.4.268/src/renderer/src/web/preload-api/host-capabilities/web-mobile-api.ts)
- Keep the entire dedicated home and Orca profile private and back them up consistently. On a non-temporary profile, headless Orca keeps the encryption key adjacent to protected credential files and may bind it to the host machine ID. Files and backup access therefore confer credential access, and a restore on a different machine can require reconnection. Keep `ORCA_TELEMETRY_DISABLED=1`; this is independent of agent-state rule downloads and optional external services. Native cloud relay, Orca Cloud connector setup, cloud authentication, and provider sign-ins are separate capabilities. [Credential storage](https://github.com/stablyai/orca/blob/v1.4.268/src/main/orcad/credentials/orcad-secret-protection-gap.ts), [telemetry opt-out](https://github.com/stablyai/orca/blob/v1.4.268/src/main/telemetry/consent.ts)

## Teams, workers and local schedules

- The GitHub API confirms [madslundt/ChessMate](https://github.com/madslundt/ChessMate) and [madslundt/Daythread](https://github.com/madslundt/Daythread) both use `main` and are public. ChessMate is self-hosted chess training with React, FastAPI, PostgreSQL and Stockfish. Daythread is a private-audio product with Omi and phone capture, upload, local-first transcription, diaries and source-grounded recall. Repository access grants do not include operational data or separately maintained services. [HomeCompute](https://github.com/madslundt/HomeCompute) uses `master`.
- A paired owner uses Orca's Bots sidebar or the official browser's authenticated `window.api.runtime.call({method, params})` bridge. `bots.list` and `bots.groups.list` provide inventory. `bots.create` accepts `name`, `agent`, `launch:{model}`, `permissionMode:'ask'`, and a short `seed` written to SOUL.md. `bots.update` can set the agent, model and permission. `bots.groups.create` takes `{name,botIds}`; `bots.groups.update` takes `{groupId,revision,botIds,replyMode:{kind:'mentions'}}` with the current revision. Group creation needs a supported installed CLI because members get separate native sessions. Local Unix RPC is stamped as a CLI and intentionally cannot perform owner bot creation or group mutation. `orca bot create --offer` only offers a bot from an existing bot chat and requires owner confirmation. [Bot RPC](https://github.com/stablyai/orca/blob/v1.4.268/src/main/runtime/rpc/methods/bots-create.ts), [group RPC](https://github.com/stablyai/orca/blob/v1.4.268/src/main/runtime/rpc/methods/bot-groups.ts), [web pairing bridge](https://github.com/stablyai/orca/blob/v1.4.268/src/renderer/src/web/preload-api/runtime/web-runtime-api.ts)
- Group member sessions are distinct, while a long-lived bot's SOUL.md and MEMORY.md follow that bot. Reusing a single persistent bot across groups shares its memory and host privileges. Use per-project PO and Group, plus common source-controlled specialist roles in per-task workers. Orca does not establish a filesystem or credentials boundary between agents that run under the same service user. Keep those materials outside that host profile and require operator approval for cloud escalation and privileged writes. [Bot security](https://orca.dev/docs/bots/security), [bot group runtime](https://github.com/stablyai/orca/blob/v1.4.268/src/main/bots/bot-group-runtime.ts)
- Use `orca orchestration worker-start --agent opencode --worktree new-top-level --repo id:<id> --setup skip --spec-file <file>` for supervised coding and QA workers, then inspect `worker-show` and `worker-read`. OpenCode's `--model` switch is limited to workers targeting an existing worktree. A fresh worktree uses the OpenCode config model. The headless CLI also supports `repo add`, `repo set-base-ref`, and `reference add` to register projects, pin the base branch and link issues or PRs. [CLI reference](https://orca.dev/docs/cli/reference), [worker contract](https://github.com/stablyai/orca/blob/v1.4.268/src/cli/specs/orchestration-worker-specs.ts)
- `orca automations create --name <name> --bot <name> --trigger '0 9 * * 1-5' --timezone Europe/Copenhagen --runs-in new --results-to chat --prompt <prompt> --disabled --json` creates a native local schedule from the host CLI once the native bot exists. `automations list` and `automations edit` let an operator reconcile or enable by ID. A fixed read-only GitHub request can use public GitHub API data or a scoped credential and send results to bot chat. Native GitHub event intake and replies require Orca sign-in and installation of the Orca GitHub App. GitHub sends repo, actor and event metadata and relevant issue/PR content to Orca Cloud, which queues events and relays them to the local runtime. Replies in the originating thread go through the Orca App. Other GitHub work uses the host's own `gh` login. Keep event delivery disabled pending approval. [Automation documentation](https://orca.dev/docs/cli/automations), [Bot connectors](https://orca.dev/docs/bots/connectors), [event input scope](https://github.com/stablyai/orca/blob/v1.4.268/src/cli/automations/automation-event-trigger-spec.ts)

## OpenCode

[OpenCode v1.19.6](https://github.com/anomalyco/opencode/releases/tag/v1.19.6) uses the `opencode` bot agent. Orca supports that ACP path starting at OpenCode 1.18.31. Orca requires 2.0.14 or later for `opencode2`. v1.19.6 x64 glibc package SHA-256 `47734e08968b30cc22a0bffb6d9feeed76ad4aa743213a12122040392d09a057`. The baseline x64 asset SHA-256 is `8443113b3f3dfebf8b0fa91c4377e5519a62b9231732d9344a5df001e4a852b3`. Place the executable where Orca's login-path resolver can find it, for example `$HOME/.opencode/bin/opencode` or `/usr/local/bin/opencode`. [Orca ACP minimum versions](https://github.com/stablyai/orca/blob/v1.4.268/src/main/acp/launch/acp-minimum-versions.ts), [OpenCode launch selection](https://github.com/stablyai/orca/blob/v1.4.268/src/main/acp/launch/acp-launch-registry.ts)

OpenCode v1.19.6's global config uses `model: "homecompute/automation-moe"`, `enabled_providers: ["homecompute"]`, `provider.homecompute.npm: "@ai-sdk/openai-compatible"`, `provider.homecompute.options.baseURL: "https://llm.home.arpa/v1"` and `provider.homecompute.models.automation-moe.options` with `reasoningEffort: "xhigh"` and `chat_template_kwargs: {"enable_thinking": true}`. Supply only the approved model-scoped credential or the approved keyless path. The SDK maps the camel-case reasoning option to `reasoning_effort` on the wire. Disable model catalog fetch, auto-update and session sharing in this environment. [OpenCode v1.19.6 option mapping](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/opencode/src/provider/transform.ts), [HomeCompute reasoning requirements](../openbot-agent-setup.md)

## Disposable smoke tests

- An unprivileged Debian-based Docker container ran the verified ARM64 server bundle under its bundled Node 24.22.1. The first loopback-only test returned HTTP 404 without the renderer and rejected network pairing. With the official renderer installed and the container port published solely on host loopback, both browser paths returned HTTP 200. Runtime and native mobile pairing offers worked while supervised startup kept links out of logs.
- Chromium followed the disposable web pairing link, connected to the runtime WebSocket, showed the Bots section, and returned a paired device ID and capabilities. The owner bridge created a synthetic OpenCode PO with the configured model and Ask permission. The bot survived the container restart. Native Groups then created and listed its synthetic project group and set mention-only replies. The browser logged one unrelated upstream linked-Linear update method error.
- Native CLI created and listed a disabled weekday automation targeting the synthetic OpenCode PO. The saved automation identified its scheduler as the local host service.
- Actual OpenCode 1.19.6 completed a synthetic streamed request to an isolated test fixture which received the Chat Completions path, `model: "automation-moe"`, `reasoning_effort: "xhigh"`, `chat_template_kwargs.enable_thinking: true`, and coding tools. This establishes client serialization and response handling. Gateway access and a real Spark inference request remain target-host checks.
- A synthetic PO turn in the authenticated browser launched an actual supervised OpenCode worker through the native orchestration CLI. The worker ran in a new Git worktree and reached `ready` with input accepted, and its native transcript contained the expected fixture response. The local model fixture scripted the tool call and response, so the smoke establishes the execution path rather than model judgment. No GitHub write occurred.
- Configure the server's agent surface through paired `settings.update` using `{agentDefaultSurface:'chat',nativeChatPermissionMode:'ask'}` and set the Orca agent permission through paired `settings.mutateAgentLaunch` using `{type:'permission',choice:'ask'}`. A fresh profile uses Terminal as the default surface and Full access as the default permission. The test's OpenCode terminal worker timed out before readiness; the structured worker succeeded once the host preferred Chat. [Host launch policy](https://github.com/stablyai/orca/blob/v1.4.268/src/main/agent-launch/agent-launch-mode.ts), [agent permission mutation](https://github.com/stablyai/orca/blob/v1.4.268/src/shared/rpc-contract/agent-launch/agent-launch-settings-params.ts)
