# Caveats for a top-notch GB10 multi-model setup

Verified: 2026-08-26

Scope: one 128 GB NVIDIA GB10/DGX Spark-class appliance, the repository's
current Qwen3.6 Phase C baseline, proposed small/coding/reasoning challengers,
local Danish speech, and explicit cloud fallback. External claims use only
publisher, runtime-project, or vendor documentation.

## Verdict

The architecture is strong, but it is **not yet a top-notch production setup**.
The repository has the right gates; most are still hardware-dependent and not
run. The current [Compose baseline](../../deploy/compute-node/compose.yaml) is one
Qwen3.6 process with six names, no accepted priority/admission layer, and no
model manager. It is a deliberately conservative Phase C test fixture, not a
five-model resident deployment.

One recommendation should change immediately at the policy level: keep MTP off
in the production candidate until the exact pinned GB10 tuple passes a long
soak. NVIDIA stopped enabling MTP by default for this exact Qwen3.6 Spark
profile and warns that lower context/concurrency/batch limits do not guarantee
protection from a host freeze. The repository now defaults it off in
[the example environment](../../config/compute-node.env.example) and retains the exact
MTP-on value only as a commented experimental tuple.
[NVIDIA NemoClaw release note](https://docs.nvidia.com/nemoclaw/user-guide/deepagents/release-notes/2026/8/4)

Severity meaning: **Critical** blocks production; **High** blocks promotion of
the affected role; **Medium** requires an operational control before routine
use.

## Prioritized caveats

| Priority | Caveat and consequence | Required mitigation | Acceptance evidence |
| --- | --- | --- | --- |
| P0 · Critical | **Qwen3.6 MTP can threaten host stability.** The configured `mtp` speculative path may freeze the appliance, taking text and co-resident speech down together. | Make MTP-off the safe production candidate. Keep MTP-on as a separate immutable experiment; promote it only on a fully pinned OS/driver/container/model/config tuple. | MTP on/off quality and performance record plus forced cancellation/OOM and a 24-hour M4 mixed-load soak with no host freeze, unrecovered OOM, or tool/JSON regression: [V-MEM-001, V-OPS-008](../verification-strategy.md). |
| P0 · Critical | **128 GB is one shared CPU/GPU ceiling, not 128 GB of dedicated VRAM.** The OS, display reservation, page cache, weights, KV cache, graphs/workspaces, containers, STT/TTS and telemetry compete for the same memory. NVIDIA lists 128 GB unified memory at 273 GB/s; its UMA guidance also says ordinary GPU-memory reporting is incomplete. Large-model fit does not imply useful latency or coexistence. [Hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html), [UMA known issue](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html) | Keep one shared model resident. Add a small reserved `home` process only if measured P0 latency requires it. Treat coder and 120B reasoner as mutually exclusive jobs, and budget globally; vLLM's `gpu_memory_utilization` is a per-process limit, not a cross-process reservation. [vLLM cache configuration](https://docs.vllm.ai/en/stable/api/vllm/config/) | Measured idle/load/M4 peaks including filesystem cache and audio services, at least 10% headroom, predictable allocation-failure recovery, and a signed resident-set decision: [V-MEM-001](../verification-strategy.md). |
| P0 · Critical | **There is no accepted QoS isolation yet.** All aliases currently hit one FCFS-style process with concurrency two. A long Codex prefill or meeting job can delay a Home Assistant request; adding more processes can instead cause memory and bandwidth contention. | Put bounded admission queues ahead of each workload class; reserve P0 capacity or a small process if necessary; cap prompt/output/concurrency by authenticated consumer; pause P3/P4 work under pressure. If vLLM request priority is used, explicitly select and verify its priority scheduler rather than assuming aliases imply priority. | M1-M6 mixed-load results with queue time, p95/p99 TTFT, starvation and memory/preemption telemetry. M4 must meet the 750 ms model TTFT and 2.5 s first-audio gates: [V-PERF-001](../verification-strategy.md). |
| P0 · Critical | **A model ID is not a deployment recipe.** Qwen3.6 needs its Qwen reasoning/tool parsers; Coder-Next needs `qwen3_coder` and is non-thinking; gpt-oss requires Harmony; Nemotron uses a custom reasoning parser. Inheriting the current flags can produce malformed tool deltas, lost reasoning state, hangs, or silently plain-text “tool calls.” [Model audit](attached-model-recommendations-audit.md) | Maintain one immutable launch profile per model/runtime/quantization/template/parser/context tuple. Never switch only `MODEL_ID`. Validate both direct vLLM and Caddy/LiteLLM Responses streaming, cancellation, compaction, parallel calls and real MCP tools before alias promotion. TensorRT-LLM is a model-specific challenger, not a blanket drop-in replacement. | Full [V-CODEX-001 and V-GW-001](../verification-strategy.md) pass, including exactly one terminal event, call-ID/JSON integrity, malformed-call handling and no lost tool result. |
| P0 · Critical | **Tool-call syntax is not tool-call safety.** Even a schema-valid model can choose the wrong entity, arguments, or action, and a small router can confidently send a sensitive task to cloud or a weak model. Self-reported model confidence is not an authorization control. | Route sensitivity and cloud eligibility deterministically from authenticated identity and data classification. Use deterministic Home Assistant intents first; expose least-privilege tools; validate exact schema/entity/arguments below the model; require a separate approval object for consequential writes; fail closed. Shadow-test any learned router before activation. | 98% exact normal-action corpus, zero hallucinated executed entities, 100% safety-critical denials, plus a routing confusion matrix that separately caps dangerous/local-to-cloud false negatives: [V-HA-001/002 and V-SEC-005/009](../verification-strategy.md). |
| P0 · Critical | **The vLLM API key is not a complete security boundary.** vLLM documents unauthenticated non-`/v1` and control routes; `--trust-remote-code` executes publisher code; writable caches are trusted code/data; shared prefix caching can expose a cross-tenant timing signal. [vLLM security](https://docs.vllm.ai/en/stable/usage/security/), [prefix-cache isolation](https://docs.vllm.ai/en/stable/design/prefix_caching/) | Expose only the Caddy/LiteLLM allow-listed API paths; firewall every runtime, metrics, distributed and management port; never enable dev/profiler/dynamic-LoRA routes; pin and review remote code or remove trust when unnecessary; restrict cache writers. Add a secret `cache_salt` per household/profile trust boundary or disable cross-tenant prefix reuse. | LAN/untrusted-segment port scan, unknown-path denial, per-key revocation/cross-profile tests, cache-permission inspection and timing-side-channel test: [V-SEC-001/003/004/007](../verification-strategy.md). |
| P1 · High | **Native 256K/262K context is not a usable default promise.** The repository correctly caps Phase C at 32K; Hermes needs a separately qualified 64K. Long prompts multiply KV demand, preemption/recomputation, TTFT and compaction loss. vLLM states that KV preemption can materially hurt end-to-end latency. [vLLM optimization guide](https://docs.vllm.ai/en/stable/configuration/optimization/) | Publish per-alias input/output/context caps and conservative compaction thresholds. Test retrieval position, instruction retention, tool schemas and cancellation at 8K/32K/64K and the largest genuinely needed context; do not expose 262K merely because the card advertises it. | Long-thread Codex compaction pass, 64K Hermes memory/mixed-load qualification, and no unsupported-claim/tool regression across context buckets: [V-CODEX-001, V-MEM-001](../verification-strategy.md). |
| P1 · High | **FP8 KV, NVFP4/FP8 weights and MTP are separate quality/performance variables.** FP8 KV saves memory, but vLLM notes that scales may fall back to `1.0` when the checkpoint has none and recommends dataset calibration for highest quality. Quantization and batching can alter borderline tool/JSON behavior even when headline accuracy looks close. [vLLM FP8 KV documentation](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/), [vLLM speculative-decoding documentation](https://github.com/vllm-project/vllm/blob/main/docs/features/speculative_decoding/README.md) | Inspect effective KV scales. Compare auto/BF16 KV versus FP8 KV and MTP off/on on long-context, Danish, coding and tool fixtures. Treat Q4, Q8, FP8, MXFP4 and NVFP4 as distinct artifacts; select on accepted task time and reliability, not tokens/s or bit count. | Repeated A/B scorecards reporting draft acceptance, end-to-end task time, schema/tool validity, review findings, long-context accuracy, memory and error bars under identical workloads: [benchmark controls](../verification-strategy.md). |
| P1 · High | **On-demand models create user-visible cold starts and rollback gaps.** NVIDIA notes model selection can add up to about 30 seconds in a Spark example, while very large vLLM loads can take minutes. A heavyweight model cannot be blue/green loaded if both copies exceed memory. [NVIDIA Open WebUI playbook](https://github.com/NVIDIA/dgx-spark-playbooks/blob/main/nvidia/open-webui/README.md), [NVIDIA vLLM playbook](https://github.com/NVIDIA/dgx-spark-playbooks/blob/main/nvidia/vllm/README.md) | Use an explicit job state (`queued/loading/ready/running`), drain requests, unload before heavyweight activation, warm and run parser/readiness canaries before remapping. Keep `home` independent of swaps. Isolate compile caches by qualified tuple and document cold rollback time. | Cold/warm load distributions, alias-switch and rollback timings, aborted-load recovery, and proof that repeated P0 voice requests stay within SLA during coder/reasoner activation: [V-OPS-002/006, V-PERF-001](../verification-strategy.md). |
| P1 · High | **Danish claims still need local evidence.** Multilingual model cards do not establish Danish schema, names, dialects or code-switch quality. Parakeet is a useful Danish STT candidate but does not prove noisy mixed-language meeting quality; Whisper Turbo trades decoder depth for speed. Piper is the maintained integration baseline, while Røst is more natural in a small publisher study but uses an archived custom runtime, stochastic output and unresolved production-license details. [STT evaluation](stt-model-evaluation.md), [Danish TTS recommendation](danish-tts-recommendation.md) | Use native-Danish household and meeting corpora, including names, numbers, negation, dialect/noise and Danish-English switches. Preserve raw transcripts. Keep Piper as the deterministic operational fallback; promote Røst only after license, Wyoming adapter, repeatability, pronunciation and latency pass. Reject any text model that misses Danish factual/JSON gates regardless of English benchmarks. | [V-GEN-001, V-STT-001 and V-TTS-001](../verification-strategy.md): stated WER gates, 95% pronunciation pass, MOS ≥3.5/5, TTFA ≤750 ms, RTF ≤0.5, three native listeners for TTS, plus mixed-load repeats. |
| P1 · High | **Current health and logging do not equal production observability.** `/health` can say the process is alive while the model/parser/alias path is unusable. Disabling Uvicorn access logs protects privacy but removes runtime request evidence; without gateway metadata, queue and fallback faults become invisible. | Add model-readiness and end-to-end synthetic canaries. Export metadata-only actual-model, route, queue, TTFT/TPOT, preemption, KV pressure, unified-memory/page-cache, temperature/power, cold-load, OOM, restart, disk and cost metrics. Keep request IDs out of metric labels and prompt/tool/audio content out of all logs. | Dashboard/alerts plus fault injection and unique privacy canaries across edge, gateway, runtime, journal and metrics: [V-SEC-006/008, V-OPS-001/002/003/008](../verification-strategy.md). |
| P1 · High | **“Latest” software and cloud aliases can regress a qualified tuple.** GB10 is ARM64/SM121 and runtime/kernel support changes quickly. NVIDIA's July 2026 stack improved UMA OOM handling, but partner GX10 update timing can differ. Model, tokenizer, template and parser can drift independently; cloud aliases can also change behavior. [DGX Spark releases](https://docs.nvidia.com/dgx/dgx-spark/release-notes.html), [GPT-5.6 Sol model page](https://developers.openai.com/api/docs/models/gpt-5.6-sol) | Pin OS/firmware/driver/container digest/model and tokenizer commits/code/template/parser/config. Stage security updates, regression-test them, and retain a bootable prior manifest. Use a cloud snapshot when the provider exposes one; otherwise treat the alias as mutable and run scheduled canaries. | Signed release manifest/SBOM/license record, clean rebuild, candidate soak, failed-post-switch rollback rehearsal, and cloud behavior canary: [V-SEC-007, V-OPS-006/007/008](../verification-strategy.md). |
| P1 · High | **Cloud fallback changes privacy, behavior, availability and cost.** OpenAI API content is not used for training by default, but default abuse-monitoring logs can retain prompts/responses for up to 30 days; ZDR and EU processing require eligibility and have feature limits. Sol currently costs $4/M input and $20/M output, uses higher pricing above 272K input, and its promotion lasts only through 2026-11-21. [OpenAI data controls](https://platform.openai.com/docs/models/default-usage-policies-by-endpoint), [Sol pricing](https://developers.openai.com/api/docs/models/gpt-5.6-sol) | Classify/redact before submission; set `store:false`; never cloud-fallback private aliases/audio; verify the organization's actual retention/residency setting. Add per-consumer daily/monthly budgets, context/output caps, timeout/circuit breaker, explicit fallback reason and cost telemetry. Use Terra for qualified ordinary escalation and Sol only where its measured gain justifies cost. | Forced-local-failure packet/provider audit with zero private egress, retention/ZDR configuration evidence, budget-exhaustion and provider-rate-limit tests, monthly cost forecast from replayed traces, and output/tool parity review: [V-SEC-009, V-CODEX-E2E-001](../verification-strategy.md). |
| P2 · Medium | **The 1 TB SSD can fill long before the model shortlist is exhausted.** Active and rollback containers, Hugging Face snapshots, FP8/NVFP4/GGUF variants, temporary downloads and compile caches can duplicate large artifacts. Frequent pull/delete cycles also create avoidable SSD writes; exact drive endurance is vendor-specific and should not be assumed. [DGX Spark hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html) | Keep one canonical cache, record compressed/downloaded/unpacked size before approval, enforce the repository's active+rollback-only policy and 80%/90% watermarks, remove only manifest-unreferenced artifacts, and monitor NVMe SMART health. Use external storage only after an ADR and performance/recovery test. | Per-artifact storage bill, low-space alert/change-freeze drill, recoverable cleanup rehearsal, clean rebuild timing and SMART baseline/trend: [V-OPS-005/007](../verification-strategy.md), [storage ADR](../adr/005-storage-strategy.md). |

## Recommended production shape

The best target for one GB10 is therefore:

1. one MTP-off, qualified shared model resident;
2. optionally one small reserved `home` model only if M4 measurements justify it;
3. mutually exclusive, queued coder/reasoner activation with explicit cold-load state;
4. independent speech services, with CPU Piper retained as the resilient TTS fallback;
5. deterministic identity, safety, routing and cloud-egress policy outside the model;
6. immutable per-model recipes and promotion based on repository-shaped tasks;
7. cloud Terra/Sol escalation only for classified workloads, with privacy and spend controls.

“Top notch” should mean every Critical and High row has a dated evidence artifact
for the exact release tuple. A publisher benchmark, native context claim, or one
successful demo is candidate-selection evidence, not production acceptance.
